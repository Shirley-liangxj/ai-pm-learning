# 一、机器学习（ML）

## 1.机器学习三大范式

### 监督学习  ：有标准版答案 （标签）   

使用监督学习模型，存在如下约束：  eg.SFT（监督微调）   **分类，回归**

1. 模型效果取决于标注数据质量，标注错误、标准不一致会直接导致模型效果变差，产品需输出标注规范，校验标注质量。

2. 仅能处理训练见过的场景，遇到全新未知案例识别能力不足，需要收集线上坏案例持续补充样本迭代模型。

3. 部分判定带有主观性，不同人判断存在差异，模型输出会有松紧波动，需细化业务规则，增加人工复核兜底。

### 无监督学习  ：无标准答案，自动分组 

采用无监督学习模型，模型自主挖掘数据内在特征，存在以下业务限制： eg.Embedding向量化    **聚类**

 1. 模型仅按照相似度做分组聚类，无法自动判断分组是否具备业务价值，需要业务人员人工评估分组结果有效性。

2. 聚类数量、分析维度需要人工配置调参，模型不会自动输出最优分组，需要产品与数据团队迭代调试。

3. 异常检测输出仅代表样本属于少数偏离样本，不等于业务问题，不可直接作为判定结论，必须接入人工复核，避免误判。

### 强化学习  ：试错+奖励 agent做动作，环境给奖励（不用标签，需要能定义的奖励）

模型能力边界   eg.RLHF（大模型人类反馈）

1. 奖励函数设计至关重要，设置不合理会出现奖励黑客：模型钻规则漏洞拿到高奖励，却偏离产品真实业务目标，奖励信号需要贴合业务价值，避免单一指标。

2. 训练不稳定，开发成本高、迭代周期长，工程实现门槛高于监督学习。

3. 效果不能仅依靠离线指标判断。离线指标基于历史测试数据集，仅作参考，不等同线上真实效果；强化学习需线上或高仿真环境反复验证，整体风险、成本更高。

### PM选型判断框架（给你一个AI需求，你怎么选型）

 接到AI需求，三步思考：

1.有没有带标准答案的标注数据？

有 → 优先监督学习（SFT）

2.没有标注数据，业务目标是什么？

- 挖掘分组、找异常 → 无监督学习（向量化、聚类）
- 优化长期策略，可以定义奖励 → 强化学习（RLHF）

3.评估风险业务能不能接受

- 监督学习：能不能承担标注成本
- 无监督学习：业务能否接受没有标准答案的输出
- 强化学习：奖励函数能否设计，成本、稳定性是否接受

### 哪些场景不适合上机器学习ML

 1. 业务逻辑简单，if‑else规则可实现

2. 需要强可解释性（金融合规、法律判定），模型黑盒不好追责

3. 历史样本数据太少

4. 一次性不重复的决策，没有同类历史案例

5. 目标主观，标注人员意见分歧大，要先拆解客观子维度

### 业务转ML任务四步骤

 1. 明确：模型支撑什么业务决策

2. 倒推输出粒度：数字→回归；类别→二分类/多分类；分组→聚类

3. 判断标签：有标签=监督学习；无标签挖掘结构=无监督学习

4. 和算法工程师对齐任务，避免预期不一致

## 二、RAG检索增强生成

本质：开卷考试，**先检索知识库文档，连同用户问题交给大模型生成答案**  

 把检索到的文档片段+问题拼成Prompt发给大模型

- 解决大模型原生3个问题：知识过时、缺少私有内部资料、缓解幻觉
- 边界

1.知识库没有资料，依旧回答出错

2.检索会召回无关文档，造成答案跑偏

3.只能缓解幻觉，不能彻底消除幻觉，关键业务要人工复核

**要宽进严出（先拉召回，再精确）**

Q1：RAG和微调（SFT）的区别？什么场景选哪个？

✅RAG：适合知识频繁更新、需要溯源来源；不改动模型本身。

✅微调：适合改变模型说话风格、输出格式；改动模型权重。

💡两者不互斥，可以组合使用。

Q2：用户反馈回答“答非所问”，怎么排查？

分两大环节定位：

1. 检索环节：没有检索到正确相关文档；

2. 生成环节：拿到了正确材料，但prompt设计不好，模型没有用好检索回来的材料。

RAG不改动大模型，外挂知识库；召回管找资料，生成管写答案，两者分开评估。

## 三、数据集，过拟合

### 三个数据集

1. 训练集：平时作业

模型在这里学习、调参，直接看标准答案训练。

2. 验证集：模拟考试

训练过程中用来调超参数，判断模型好坏，决定要不要停止训练。模型不直接学它的标准答案。

3. 测试集：正式期末考

全程训练不能碰，用来模拟真实线上环境，做最终能力评估。 

### 过拟合

模型死记硬背训练集样本，训练集分数极高；

但是没学到通用规律，遇到新的真实数据表现很差，就是上线“拉胯”。

### AI‑PM要记住 

1. 不能只看训练集指标，不能拿训练集数据评判线上能力。

2. 测试集必须和真实线上分布一致，不能泄露给训练过程。

3. 评审模型报告，要重点看测试集指标，不是训练集漂亮数字。

## 四、精确率、召回率

**产品经理要参与定阈值、定业务策略，不能直接拿来工程师默认0.5阈值就上线。**

### 精确率Precision：报出来的结果里面，有多少是真正对的

捕鱼：捞上来的网里面，真正目标鱼占比。

精确率高：捞上来基本都是目标鱼，但很多目标鱼漏掉。

### 召回率Recall：所有真实正例里面，被模型找出来多少

捕鱼：全部真实目标鱼，被你捞上来的比例。

召回率高：目标鱼大多捞上来，但网里面混很多杂鱼。

**记忆口诀：精确率管纯度，召回率管覆盖面**

和准确率Accuracy不是一回事

- 准确率Accuracy：全部样本里面预测正确的占比（正确正例+正确负例）
- 精确率/召回率：只关心「正例」这一侧

⚠️样本不均衡，准确率会骗人

举例：一万条内容，只有10条违规。模型全部输出正常。

准确率99%看着很好，召回率=0，一条违规都没抓住。

### F1是什么、什么时候用 

F1分数：精确率和召回率的调和平均值。**不能作为上线依据**

 精确率、召回率都高，F1才高；任意一个很差，F1明显下跌。

适用场景：

1. 离线对比多个模型好坏、选型的时候，作为综合参考指标。

2. 业务还没有明确偏向保精确还是保召回。

 

⚠️重点：F1不是上线决策点

两个模型F1相同，漏报误报带来的业务风险可以完全不一样。

上线最终看业务代价，不能只看F1数值。

 

### PM权衡决策思考框架

做阈值决策，先问两个问题：

1. 漏报一个正例代价多大？（本该抓到，结果漏掉）**召回**

2. 误报一个负例代价多大？（本来正常，被模型错误命中）**精确**

# 二、LLM（大语言模型）

1. 生成原理：大模型逐token预测下一个词，并非真正理解。

2. Temperature温度

- 外部API传入参数，模型不会自行变化
- 趋近0：分布陡峭，输出稳定，适合代码、JSON，易重复，常用0.1‑0.3
- 接近1：分布平坦，输出多样，适合创意写作
- 温度≠0，相同输入回复会不一样，属于概率采样；温度不能消除幻觉

3. 预训练 vs 后训练

- 预训练（Base基座）：目标预测下一个token，海量文本习得知识逻辑，决定能力上限；只会续写，听不懂指令。
- 后训练改造为助手
- SFT监督微调：问答样本，教会按指令作答
- RLHF人类反馈强化学习：对齐人类偏好

**预训练决定能力，后训练决定是否听话。**

4. PM要点

- 模型聪明≠输出事实正确，需要RAG等兜底
- 随机性是可配置特性，不是bug
- 模型是计算生成，会产生幻觉

## Transformer

### 1. 定位

Transformer是主流LLM底层基础架构，最初用于机器翻译；GPT系列属于Decoder‑only，只用解码器部分。（侧重文本生成）

### 2. 自注意力 Self‑Attention

任意token之间可以直接计算关联，不需要信息逐层传递，长距离依赖更容易建模。**注意力是动态决定要看哪些词**

⚠不是有注意力就等于无限上下文，窗口受显存、位置编码、工程实现约束。

### 3. 多头注意力

多组注意力头并行运算，每个头捕捉文本不同维度关联，结果合并，理解更全面。

### 4. 对比旧RNN/LSTM两大优势

- 支持大规模并行训练，充分利用GPU算力，可以训练超大参数模型。
- 更容易建模长距离依赖，相隔很远的token可以直接建立逻辑关系。

### 5. 产品侧核心约束

- 架构决定能力边界：长文本后半段效果衰减、多轮对话截断逻辑，来自注意力计算与窗口设计。
- 自注意力计算量随序列长度**平方增长**，输入文本越长，耗时、调用成本越高。
- 产品方案：不要直接把整篇文档塞进prompt，使用RAG、摘要、分层检索优化。

## 上下文窗口

### 1.上下文窗口

- 定义：模型单次能处理最大token数量
- 占用窗口：系统提示词、历史对话、用户输入、RAG片段、工具返回、模型输出
- 超限后果：内容直接丢弃，模型物理看不到，不是记性差

### 2.窗口不是越大越好，权衡3点

- 成本：token越多费用越高，超长输入会溢价
- 延迟：token越多，响应越慢
- 效果：冗余信息会稀释关键内容，降低回答质量

### 3.长文档两种方案

1.全量塞入大窗口：可读全文；成本高，长文本后半段效果衰减

2.RAG检索：仅送入相关片段，成本可控；检索出错则答案出错

### 4.AI‑PM核心启示

1.选型优先看业务实际需要的上下文，不要盲目追求超大窗口

2.长文档、长对话，提前设计中间遗忘的应对方案

3.窗口与RAG互补：窗口决定能塞多少，RAG决定该塞什么

4.成本测算：厂商超长输入计费存在溢价，不能简单线性计算

##  幻觉问题

**高发场景**

1.冷门长尾知识

2.精确数字、引用、编号

3.训练截止时间之后的新事件

**分层缓解手段**

1.Prompt层：降低temperature；先摘抄原文再回答

2.检索层：RAG做外部资料约束；Rerank优化检索质量    RAG不能消灭幻觉，检索素材差依旧幻觉

3.验证层：Best‑of‑N多次生成交叉比对

4.呈现层：Citation引用溯源，方便用户核对

5.产品兜底：检索不到就拒答；高风险场景人工复核

6.用户层：做好预期管理，提示AI可能出错

**业务选型策略**

- 高风险（医疗/金融/法律）：宁可不答，不能乱编，拒答+溯源
- 低风险（创意文案）：允许适度编造
- 中间场景（知识库客服）：RAG+溯源，性价比最高

幻觉无一招解决，按业务风险做多层组合方案

### **PM排查bug两类badcase**

1.检索问题：没拿到正确材料 → 优化检索链路

2.生成问题：材料正确，模型用错 → 优化prompt、生成逻辑

##  Agent入门

### 1、三种主流Agent形态

1. 电脑操作Agent：模型操控屏幕、浏览器。支付、删除等高风险动作，必须人工确认。

2. 深度研究Agent：自动多轮搜索、交叉验证，输出调研报告，运行耗时久。

3. 多Agent协作：复杂任务拆分为多个子Agent并行执行，结果汇总。

**PM判断框架：要不要使用Agent**

1. 是否是多步骤、需要调用外部工具的任务？不是则不用Agent。

2. 每一步是否可以做结果验证？

3. 出错代价：不可逆高风险操作，强制人工确认。

4. 业务是否接纳成本、延迟的不确定性？

不是所有场景适合Agent。优先单轮prompt或者Lam固定工作流；只有任务多步骤、步骤不确定，需要动态调用工具，才选用Agent，同时做好确认、步数、成本、日志的产品约束。

MCP接通工具，Skills规范用法；Agent能力强，但伴随失控、成本、错误累积风险，能简单就不复杂。

**MCP不能消除Agent本身风险。**

### 2、MCP & Skills（高频）

#### 1. MCP定义

MCP（模型上下文协议）：工具对接通信协议，类比USB‑C，标准化AI应用对接外部系统，降低多Agent对接多数据源的集成复杂度。**(是协议）**

PM价值：新增工具大多靠配置，消除大量重复对接胶水代码；仅负责连通，不含业务逻辑。

 三层架构

- MCP Host：AI上层应用，整体调度    （eg. Claude ,cursor)
- MCP Client：Host内部组件，可多个，对接不同Server 
- MCP Server：提供能力的服务端（本地/远程） **(真正干活的程序)**

MCP只规定工具、上下文交换，Agent循环逻辑由Host实现。

调用流程：Client获取工具列表→传入模型→模型决策调用→Server执行返回结果。

3. 三大原语

- Tools：执行动作，可修改数据，需权限管控
- Resources：只读获取上下文，不改动数据
- Prompts：预制提示模板

4. 三者分工

- Function Calling：模型输出调用格式，决定调用哪个函数
- MCP：连接协议，打通外部系统
- Skills：业务SOP，规定任务怎么做

链条：Skills定业务规范 → MCP接通外部 → Function Calling模型发起调用

MCP不替代Function Calling，二者配合；仅有连接无规范，Agent会接得上但做不对。

5. 适用场景

①多个Agent共用外部系统 ②复用连接器减少自研 ③区分只读资源与可执行工具

6. PM落地要点

- 区分：哪些用MCP对接，哪些自建Server
- Resources只读、Tools有副作用，分开设计权限
- 优先复用社区连接器，避免私有绑定
- 对外连接用MCP，对内业务约束用Skills
- 企业场景关注：安装权限、工具启用、审计日志

#### 2、Skills：程序性操作手册，可版本管理；规定调用时机、参数、异常处理。

分工：MCP负责接得上工具，Skills负责用得对工具。

##### 1、什么是Agent‑Skill

可复用的程序性知识包（**业务操作手册**），开放标准，支持多Agent复用。

对比系统提示词：系统提示词全部常驻上下文；Skill按需加载，节省token。

程序性知识正在从聊天记录外化成可版本控制的仓库资产

##### 2、核心机制：渐进披露 （Progressive disclosure）

1. 发现（对话刚开启）：启动仅加载技能name、description

2. 激活（用户提问）   ：任务匹配description，读取完整SKILL.md

3. 执行（真正干活）   ：真正需要时，才加载脚本、参考资料

关键点： description 决定是否触发，描述模糊会乱触发/不触发。**（要写的短，触发词靠前，边界清晰）**

##### 3、概念对照

概念 核心定义 

Workflow   人预定义固定流程编排LLM与工具，确定性强、可审计 

Agent        模型动态决定下一步动作，适合开放多变任务 

Function Calling / Tools 模型输出结构化指令，执行单次工具动作 

MCP Agent  对接外部工具、数据的连接协议（通路） 

Skill            可复用业务知识包，按需加载业务规范手册 

Subagent     把子任务交给另一个Agent，实现任务拆分、并行、隔离上下文 

**链条：Workflow是人写死流程；Agent模型动态决策；Function Calling做单次调用；MCP打通外部系统；Skill提供业务规则手册；Subagent拆分复杂子任务。**

Workflow vs Agent区别：Workflow步骤预先写死；Agent由模型动态判断下一步，灵活性高但风险更高。

##### 4、PM落地判断：适合/不适合Skill

✅适合：同类任务反复出现、流程稳定、多场景复用的业务规范、操作手册，多人会话需要对齐业务逻辑，优先用Skill，不要私藏大段system prompt。

❌不适合：简单一次性API、知识需要实时服务更新、频繁改动SDK文档，这类交给MCP/工具服务；Skill维护跟不上频繁变更，会制造过时流程。

##### 5、Skill编写要点

把场景、触发词、排除边界写在description；正文写执行步骤；参考资料外置到 references ，避免主文件膨胀。

Skill验收标准

准备该触发 / 不该触发测试用例，定义任务成功标准；上线后看误触发率、补救次数、手册是否过期。

##### 6、安全与评测

1. 安全：Skill可携带脚本指令，只加载可信来源，上线前审计，防范指令注入、恶意脚本。安全是一等约束。

2. 评测：Skill要有评测集，写完不等于交付，上线要验证效果。

#### 3、Skill 和 MCP关系

- MCP：管外部工具通路，解决怎么调用外部系统
- Skill：管业务流程规范，告诉Agent调用工具要遵守什么业务规则

👉二者互补，不是二选一。

架构默认组合：对外连接走MCP/Tools，对内规则规范走Skills；高风险步骤交给人工确认，三者搭配，不是互相替代。

# 三、Prompt工程

概念：Prompt工程化

把提示词做成固定模板，只替换输入变量，实现可复用、输出稳定。

## Prompt五大核心要素

1. 角色 Role

设定模型身份与看待问题的视角，决定输出风格。

2. 任务 Task

写清楚具体产出目标，拒绝模糊指令。

差：帮我总结用户反馈

好：阅读30条反馈，提炼本周Top3高频问题

3. 上下文 & 约束 Context & Constraints

- 上下文：**给模型业务参考资料**，RAG检索出来的文档就是上下文，不要依赖模型内部记忆，降低幻觉
- 约束：数据源、字数、禁止编造、脱敏规则、受众限制

4. Few‑shot / Multishot 少样本示例

提供输入输出样例，教会模型判断逻辑与格式。

- Anthropic：3‑5个高质量样例，覆盖边界case
- Google：少量即可，样例过多会死记模板
- OpenAI：样例尽量覆盖多种场景

示例片段

```Plain Text

【物流延迟】(本周提及 12 次) 用户反馈某订单发货超时。

```

5. 输出格式 Output Format

- 自由文本：仅人可读
- 结构化（列表/JSON/XML）：可被程序直接解析，Agent、Skill必须明确格式
- 只口头说“输出JSON”可靠性不足，要显式规定结构

推理模型时代提示词变化

1. OpenAI：推理模型(o系列)自带思考能力，强制分步指令反而限制解法；非推理模型CoT依旧有效。

2. Google：推理模型内部自动思考，反复写“一步步思考”会增加token、拉高成本。

3. Anthropic：thinking是模型内置能力，不完全靠Prompt逼出来。

考点：不要无脑到处复制“请一步步思考”。

## 结构化输出 JSON

一、为什么需要结构化输出

模型输出交给后端代码解析时，字段名、数据类型、结构必须固定；只输出自然语言，程序无法读取，Demo不能直接上线。

二、结构化输出四个发展阶段

1. 口头Prompt要求输出JSON（淘汰，仅Demo）

只写“输出JSON，不要其他文字”。

问题：模型容易输出多余话术、字段写错、类型错乱，依赖正则清洗，稳定性差。

2. JSON模式（legacy遗留方案）

✅保证JSON语法合法

❌不保证业务字段、数据类型正确，字段缺失、类型错误依旧会导致下游报错，业务层仍要写校验。

3. Tool Use / Function Calling 工具调用

把输出结构定义为工具入参**schema（一份数据契约/规则说明书。规定JSON里面：有哪些字段、字段叫什么、是什么类型、哪些必填、可以填哪些值。）**

效果优于JSON模式，但遵从率约86%，达不到生产100%可靠。

4. 原生 Structured Outputs（2026生产首选）

原理：约束解码 constrained‑decoding，token生成层面限制输出，严格遵守传入的Schema。

Claude、OpenAI、Gemini均已支持。

### 三、Schema设计7条核心规则（PRD直接用）

1. 尽量扁平，避免深度嵌套，嵌套容易出错甚至被模型拒绝

2. 每个字段补充 description 描述，消除歧义，提升准确率

3. 固定取值场景优先用 enum 枚举，不要自由字符串

4. 明确标注 required 必填字段，不交给模型自行判断

5. 开启 additionalProperties: false ，禁止输出额外字段

6. 示例字段顺序与schema顺序保持一致（Gemini对顺序敏感）

7. 优先用Pydantic/Zod代码库自动生成schema，不要手写，避免两边定义不一致

注意：各家大模型对schema支持不完全等价，上线前要做测试。

四、失败兜底：校验+重试

即使开启原生Structured Outputs，依然存在边界异常。

**失败场景**

1. 安全策略触发，模型拒绝回答

2. max‑token截断，JSON输出不完整

3. 语法合法，但业务语义、大小写等细节偏差

**生产稳定流程**

1. 使用官方结构化输出API

2. 应用层做业务校验

3. 校验失败：重试，处理临时错误

4. 重试失败：执行降级/人工兜底

5. 失败样本回流，反向优化Schema

⚠核心考点：开启Structured Outputs ≠ 不用校验，接口只保证语法合法，不保证业务语义正确。

### 五、PM写PRD要求

1. 写明完整字段契约：字段名、类型、required、enum、示例，作为QA校验依据

2. 明确定义失败产品策略：拒绝、截断、校验失败分别如何体验（重试/降级文案/人工），不能丢给研发决定

3. 技术方案优先选官方Structured Outputs / 工具调用，禁止只靠prompt文字约束JSON

## 系统提示词设计

1、System Prompt 与用户输入分层

1. system（系统提示）：全局设定，角色、语气、能力边界、输出格式；优先级高于用户输入，不要散写在每一轮user输入。

2. user：用户真实提问输入。

3. assistant：模型历史回答。

业务要点：产品人格、约束统一放在system，作为产品配置管理。

### 2、System Prompt需要写的3类内容

1. 身份与语气：产品角色、说话口吻。**固化在系统层**

2. 能力边界：明确可回答、拒绝回答；超纲问题处理策略。

3. 兜底话术：检索失败、模型报错、结构化输出失败时固定文案，**产品定义，不交给模型随机生成**。

3、Prompt注入（Prompt Injection）

- 含义：用户输入夹带恶意指令，试图绕过system系统设定篡改模型行为。

### **PM三点意识：**

1. system不是绝对安全防火墙。

2. **权限最小化**，Agent工具、访问数据范围尽量收紧。

3. 高风险操作**增加人工确认**，不能完全交给模型自动执行。

### 4、Prompt版本管理

1. Prompt改动少量文字就会改变输出，不能直接复制上线。

2. 拆分固定模板(system/指令) 和变量(用户输入、检索材料)，分开存储。

3. 修改必须记录版本号、变更原因；支持版本回滚。

### 5、回归测试 & 评测集（一批业务测试用例）

1. 修改prompt必须跑回归测试；大模型存在随机性，改后可能部分场景变好、部分变差。

2. 评测集：业务测试case集合，迭代prompt就要反复执行。

3. 不能只靠肉眼看几个样例就上线。

 **任何一次修改都应该在评测集上跑一次再合并**

### 6、灰度发布

1. 评测集通过≠直接全量上线，评测集无法覆盖线上全部长尾输入。

2. 小流量灰度，监控真实业务指标。

3. 新旧版本可切换，异常可以快速回滚。

4. Badcase回流：**线上错误案例**补充进评测集，后续迭代自动防护，避免重复踩坑。

### 7、完整Prompt工程流水线

需求&badcase收集 →起草Prompt →模板拆分+版本管理 →评测集回归测试 →人工抽查 →小流量灰度+指标监控 →全量上线，持续badcase回流。

```Plain Text
 # Prompt工程完整流程
1. 需求 / Badcase收集
2. 起草 Prompt(角色 / 任务 / 约束 / 示例 / 输出格式)
3. 模板化：拆分「固定模板」与「变量」，纳入版本管理
4. 评测集回归测试(哪怕只改一个词)
5. 人工抽查显著变化的用例
6. 小流量灰度 + 业务指标监控
7. 全量上线
8. 持续监控 → 新Badcase回流评测集 → 下一轮迭代
```

## CoT 思维链

1、定义

CoT（思维链）：Prompt技术，让模型先输出中间推理步骤，再给出答案，不需要微调模型，修改提示词即可。

2、CoT vs 直接提问

- 直接提问：直接输出答案，复杂任务容易跳步出错，推理黑盒。
- CoT：先推理再给结论，提升复杂任务准确率；代价：token增加、延迟升高。

3、核心优势

1. 擅长多步计算、业务规则嵌套等复杂推理

2. 可解释：能看到推理过程，适配合规、审核、需要输出理由的业务

3. 零训练成本，依靠Prompt / few‑shot（示例）实现

4. 错误可定位，方便badcase归因迭代

⚠️局限：不能保证每一步推理都正确，不能解决知识库缺失带来的幻觉。

### 4、开启方式

1. 普通CoT：Prompt直接加指令：**请一步步分析，再给出结论**。可分区输出推理过程与最终答案。

2. few‑shot CoT：**推理效果不稳时，给示例：输入→推理步骤→最终答案**；1‑3个高质量示例即可，格式统一，覆盖边界case。

5、成本取舍原则

只有答错的业务损失＞token+延迟成本，才默认开启CoT；不要全站无条件开启。

落地策略：

- 任务分流：简单问答直接输出，**复杂任务启用CoT**
- 分类器触发：轻量模型判断是否需要推理，动态决定是否加CoT指令（给理由的决策，为啥选A不选B）
- 展示折叠：推理过程可折叠，前端默认只展示最终答案
- 长度约束：限制推理最大步数、字数

6、**CoT + 结构化输出**

- 分工：CoT负责思考推理，JSON结构化输出负责交付最终结果给下游
- 要求：推理文本与JSON结果分区，不能混杂在一起，PRD要明确约定。

7、延伸考点

Self‑Consistency（自一致性）

- 原理：对同一问题多次采样多条推理路径，结果投票聚合，提升可信度。
- 代价：调用次数上升，token、延迟大幅增加。
- 适用：高风险审核、离线处理；实时聊天一般不使用。

**CoT + RAG**

- RAG：获取外部参考资料；CoT：对拿到的资料做推理分析，二者常组合使用。
- Prompt约束：推理仅限使用检索到的内容；资料不足输出「无法判断」，防止幻觉。

# 七、产品数据埋点

为什么要做数据埋点

产品优化: 通过用户行为数据反推产品改进方向，例如转化率低的商品埋点分析购买障碍

精准运营: 基于RFM模型（最近消费Recency、消费频率Frequency、消费金额Monetary）实现用户分层

渠道优化: 对比不同渠道的获客成本与转化效果，优先投放ROI高的渠道

用户画像: 统计用户设备信息（iOS/Android）、地域分布、消费偏好等特征

**应用场景**

**商品优化**: 对同类商品进行埋点对比，例如10款商品中筛选转化率最高的3款重点推广

**广告投放**: 统计不同广告位的点击率（CTR），优化素材和投放策略

**渠道管理**: 电商平台通过埋点识别优质流量来源，如淘宝直通车高转化关键词

**用户研究**: 通过消费数据反推用户性别比例（案例中女性用户占比显著更高）

**埋点三大系统**

行为追踪系统: 记录用户操作路径

事件监测系统: 捕获特定交互行为（如加入购物车）

属性采集系统: 获取用户设备信息、网络环境等元数据

**核心事件分类**

点击事件：用户操作的核心动作，每次点击代表触发操作/使用功能/进行选择

曝光事件：用户打开页面并看到内容的行为（如详情页、列表页、店铺页的打开）

停留时间事件：反映用户真实参与度，比单纯打开页面更能体现产品价值

落地页

一个简洁的首屏

一个真正的「开始」按钮

技术栈: React+Vite+Tailwind你随意选

1. 基于上节课的落地页和测评介绍页, 现在要加两个新页面。

答题页 (用户点击「开始」后进入)

页面结构:

顶部进度条: 显示「第 X 题 /共 15 题」, 进度条用主色

题目区

顶部一行小字: 「AI 基础认知」

题干:
