# 一、机器学习（ML）

## 1. 机器学习三大范式

### 监督学习：有标准答案（标签）

使用监督学习模型，存在如下约束：eg. SFT（监督微调）**分类，回归**

1. 模型效果取决于标注数据质量，标注错误、标准不一致会直接导致模型效果变差，产品需输出标注规范，校验标注质量。

2. 仅能处理训练见过的场景，遇到全新未知案例识别能力不足，需要收集线上坏案例持续补充样本迭代模型。

3. 部分判定带有主观性，不同人判断存在差异，模型输出会有松紧波动，需细化业务规则，增加人工复核兜底。

### 无监督学习：无标准答案，自动分组

采用无监督学习模型，模型自主挖掘数据内在特征，存在以下业务限制：eg. Embedding 向量化 **聚类**

1. 模型仅按照相似度做分组聚类，无法自动判断分组是否具备业务价值，需要业务人员人工评估分组结果有效性。

2. 聚类数量、分析维度需要人工配置调参，模型不会自动输出最优分组，需要产品与数据团队迭代调试。

3. 异常检测输出仅代表样本属于少数偏离样本，不等于业务问题，不可直接作为判定结论，必须接入人工复核，避免误判。

### 强化学习：试错 + 奖励

Agent 做动作，环境给奖励（不用标签，需要能定义的奖励）

模型能力边界 eg. RLHF（大模型人类反馈）

1. 奖励函数设计至关重要，设置不合理会出现奖励黑客：模型钻规则漏洞拿到高奖励，却偏离产品真实业务目标，奖励信号需要贴合业务价值，避免单一指标。

2. 训练不稳定，开发成本高、迭代周期长，工程实现门槛高于监督学习。

3. 效果不能仅依靠离线指标判断。离线指标基于历史测试数据集，仅作参考，不等同线上真实效果；强化学习需线上或高仿真环境反复验证，整体风险、成本更高。

### PM 选型判断框架（给你一个 AI 需求，你怎么选型）

接到 AI 需求，三步思考：

1. 有没有带标准答案的标注数据？
   - 有 → 优先监督学习（SFT）

2. 没有标注数据，业务目标是什么？
   - 挖掘分组、找异常 → 无监督学习（向量化、聚类）
   - 优化长期策略，可以定义奖励 → 强化学习（RLHF）

3. 评估风险业务能不能接受
   - 监督学习：能不能承担标注成本
   - 无监督学习：业务能否接受没有标准答案的输出
   - 强化学习：奖励函数能否设计，成本、稳定性是否接受

### 哪些场景不适合上机器学习 ML

1. 业务逻辑简单，if-else 规则可实现

2. 需要强可解释性（金融合规、法律判定），模型黑盒不好追责

3. 历史样本数据太少

4. 一次性不重复的决策，没有同类历史案例

5. 目标主观，标注人员意见分歧大，要先拆解客观子维度

### 业务转 ML 任务四步骤

1. 明确：模型支撑什么业务决策

2. 倒推输出粒度：数字 → 回归；类别 → 二分类/多分类；分组 → 聚类

3. 判断标签：有标签 = 监督学习；无标签挖掘结构 = 无监督学习

4. 和算法工程师对齐任务，避免预期不一致

## 二、RAG 检索增强生成

本质：开卷考试，**先检索知识库文档，连同用户问题交给大模型生成答案**

把检索到的文档片段 + 问题拼成 Prompt 发给大模型

- 解决大模型原生 3 个问题：知识过时、缺少私有内部资料、缓解幻觉
- 边界：
  1. 知识库没有资料，依旧回答出错
  2. 检索会召回无关文档，造成答案跑偏
  3. 只能缓解幻觉，不能彻底消除幻觉，关键业务要人工复核

**要宽进严出（先拉召回，再精确）**

### Q1：RAG 和微调（SFT）的区别？什么场景选哪个？

- RAG：适合知识频繁更新、需要溯源来源；不改动模型本身。
- 微调：适合改变模型说话风格、输出格式；改动模型权重。

> 两者不互斥，可以组合使用。

### Q2：用户反馈回答"答非所问"，怎么排查？

分两大环节定位：

1. 检索环节：没有检索到正确相关文档；
2. 生成环节：拿到了正确材料，但 prompt 设计不好，模型没有用好检索回来的材料。

RAG 不改动大模型，外挂知识库；召回管找资料，生成管写答案，两者分开评估。

## 三、数据集、过拟合

### 三个数据集

| 数据集 | 类比 | 说明 |
|--------|------|------|
| 训练集 | 平时作业 | 模型在这里学习、调参，直接看标准答案训练 |
| 验证集 | 模拟考试 | 训练过程中用来调超参数，判断模型好坏，决定要不要停止训练 |
| 测试集 | 正式期末考 | 全程训练不能碰，用来模拟真实线上环境，做最终能力评估 |

### 过拟合

模型死记硬背训练集样本，训练集分数极高；但没学到通用规律，遇到新的真实数据表现很差，就是上线"拉胯"。

### AI-PM 要记住

1. 不能只看训练集指标，不能拿训练集数据评判线上能力。
2. 测试集必须和真实线上分布一致，不能泄露给训练过程。
3. 评审模型报告，要重点看测试集指标，不是训练集漂亮数字。

## 四、精确率、召回率

**产品经理要参与定阈值、定业务策略，不能直接拿来工程师默认 0.5 阈值就上线。**

### 精确率 Precision

报出来的结果里面，有多少是真正对的。

> 捕鱼：捞上来的网里面，真正目标鱼占比。

精确率高：捞上来基本都是目标鱼，但很多目标鱼漏掉。

### 召回率 Recall

所有真实正例里面，被模型找出来多少。

> 捕鱼：全部真实目标鱼，被你捞上来的比例。

召回率高：目标鱼大多捞上来，但网里面混很多杂鱼。

**记忆口诀：精确率管纯度，召回率管覆盖面**

### 和准确率 Accuracy 不是一回事

- 准确率 Accuracy：全部样本里面预测正确的占比（正确正例 + 正确负例）
- 精确率 / 召回率：只关心「正例」这一侧

> ⚠️ 样本不均衡，准确率会骗人
>
> 举例：一万条内容，只有 10 条违规。模型全部输出正常。
> 准确率 99% 看着很好，召回率 = 0，一条违规都没抓住。

### F1 是什么、什么时候用

F1 分数：精确率和召回率的调和平均值。**不能作为上线依据**

精确率、召回率都高，F1 才高；任意一个很差，F1 明显下跌。

适用场景：
1. 离线对比多个模型好坏、选型的时候，作为综合参考指标。
2. 业务还没有明确偏向保精确还是保召回。

> ⚠️ 重点：F1 不是上线决策点  
> 两个模型 F1 相同，漏报误报带来的业务风险可以完全不一样。  
> 上线最终看业务代价，不能只看 F1 数值。

### PM 权衡决策思考框架

做阈值决策，先问两个问题：

1. 漏报一个正例代价多大？（本该抓到，结果漏掉）→ **召回**
2. 误报一个负例代价多大？（本来正常，被模型错误命中）→ **精确**

# 二、LLM（大语言模型）

## 基础概念

1. **生成原理**：大模型逐 token 预测下一个词，并非真正理解。

2. **Temperature 温度**
   - 外部 API 传入参数，模型不会自行变化
   - 趋近 0：分布陡峭，输出稳定，适合代码、JSON，易重复，常用 0.1-0.3
   - 接近 1：分布平坦，输出多样，适合创意写作
   - 温度 ≠ 0，相同输入回复会不一样，属于概率采样；温度不能消除幻觉

3. **预训练 vs 后训练**
   - 预训练（Base 基座）：目标预测下一个 token，海量文本习得知识逻辑，决定能力上限；只会续写，听不懂指令。
   - 后训练改造为助手：
     - SFT 监督微调：问答样本，教会按指令作答
     - RLHF 人类反馈强化学习：对齐人类偏好

> **预训练决定能力，后训练决定是否听话。**

4. **PM 要点**
   - 模型聪明 ≠ 输出事实正确，需要 RAG 等兜底
   - 随机性是可配置特性，不是 bug
   - 模型是计算生成，会产生幻觉

---

## Transformer

### 1. 定位

Transformer 是主流 LLM 底层基础架构，最初用于机器翻译；GPT 系列属于 Decoder-only，只用解码器部分（侧重文本生成）。

### 2. 自注意力 Self-Attention

任意 token 之间可以直接计算关联，不需要信息逐层传递，长距离依赖更容易建模。**注意力是动态决定要看哪些词**

> ⚠ 不是有注意力就等于无限上下文，窗口受显存、位置编码、工程实现约束。

### 3. 多头注意力

多组注意力头并行运算，每个头捕捉文本不同维度关联，结果合并，理解更全面。

### 4. 对比旧 RNN/LSTM 两大优势

- 支持大规模并行训练，充分利用 GPU 算力，可以训练超大参数模型。
- 更容易建模长距离依赖，相隔很远的 token 可以直接建立逻辑关系。

### 5. 产品侧核心约束

- 架构决定能力边界：长文本后半段效果衰减、多轮对话截断逻辑，来自注意力计算与窗口设计。
- 自注意力计算量随序列长度**平方增长**，输入文本越长，耗时、调用成本越高。
- 产品方案：不要直接把整篇文档塞进 prompt，使用 RAG、摘要、分层检索优化。

---

## 上下文窗口

### 1. 上下文窗口

- 定义：模型单次能处理最大 token 数量
- 占用窗口：系统提示词、历史对话、用户输入、RAG 片段、工具返回、模型输出
- 超限后果：内容直接丢弃，模型物理看不到，不是记性差

### 2. 窗口不是越大越好，权衡 3 点

- 成本：token 越多费用越高，超长输入会溢价
- 延迟：token 越多，响应越慢
- 效果：冗余信息会稀释关键内容，降低回答质量

### 3. 长文档两种方案

| 方案 | 优点 | 缺点 |
|------|------|------|
| 全量塞入大窗口 | 可读全文 | 成本高，长文本后半段效果衰减 |
| RAG 检索 | 仅送入相关片段，成本可控 | 检索出错则答案出错 |

### 4. AI-PM 核心启示

1. 选型优先看业务实际需要的上下文，不要盲目追求超大窗口
2. 长文档、长对话，提前设计中间遗忘的应对方案
3. 窗口与 RAG 互补：窗口决定能塞多少，RAG 决定该塞什么
4. 成本测算：厂商超长输入计费存在溢价，不能简单线性计算

## 幻觉问题

### 高发场景

1. 冷门长尾知识
2. 精确数字、引用、编号
3. 训练截止时间之后的新事件

### 分层缓解手段

1. **Prompt 层**：降低 temperature；先摘抄原文再回答
2. **检索层**：RAG 做外部资料约束；Rerank 优化检索质量（RAG 不能消灭幻觉，检索素材差依旧幻觉）
3. **验证层**：Best-of-N 多次生成交叉比对
4. **呈现层**：Citation 引用溯源，方便用户核对
5. **产品兜底**：检索不到就拒答；高风险场景人工复核
6. **用户层**：做好预期管理，提示 AI 可能出错

### 业务选型策略

| 风险等级 | 策略 | 场景 |
|----------|------|------|
| 高风险 | 宁可不答，不能乱编，拒答 + 溯源 | 医疗/金融/法律 |
| 低风险 | 允许适度编造 | 创意文案 |
| 中间场景 | RAG + 溯源，性价比最高 | 知识库客服 |

> 幻觉无一招解决，按业务风险做多层组合方案

### PM 排查 bug 两类 badcase

1. **检索问题**：没拿到正确材料 → 优化检索链路
2. **生成问题**：材料正确，模型用错 → 优化 prompt、生成逻辑

## Agent 入门

### 1. 三种主流 Agent 形态

| 形态 | 说明 |
|------|------|
| 电脑操作 Agent | 模型操控屏幕、浏览器。支付、删除等高风险动作，必须人工确认 |
| 深度研究 Agent | 自动多轮搜索、交叉验证，输出调研报告，运行耗时久 |
| 多 Agent 协作 | 复杂任务拆分为多个子 Agent 并行执行，结果汇总 |

### PM 判断框架：要不要使用 Agent

1. 是否是多步骤、需要调用外部工具的任务？不是则不用 Agent。
2. 每一步是否可以做结果验证？
3. 出错代价：不可逆高风险操作，强制人工确认。
4. 业务是否接纳成本、延迟的不确定性？

> 不是所有场景适合 Agent。优先单轮 prompt 或者 Lam 固定工作流；只有任务多步骤、步骤不确定，需要动态调用工具，才选用 Agent，同时做好确认、步数、成本、日志的产品约束。

MCP 接通工具，Skills 规范用法；Agent 能力强，但伴随失控、成本、错误累积风险，能简单就不复杂。

**MCP 不能消除 Agent 本身风险。**

### 2. MCP & Skills（高频）

#### MCP 定义

MCP（模型上下文协议）：工具对接通信协议，类比 USB-C，标准化 AI 应用对接外部系统，降低多 Agent 对接多数据源的集成复杂度。**（是协议）**

PM 价值：新增工具大多靠配置，消除大量重复对接胶水代码；仅负责连通，不含业务逻辑。

**三层架构**

| 层级 | 角色 | 示例 |
|------|------|------|
| MCP Host | AI 上层应用，整体调度 | Claude, Cursor |
| MCP Client | Host 内部组件，可多个，对接不同 Server | — |
| MCP Server | 提供能力的服务端（本地/远程）**真正干活的程序** | — |

MCP 只规定工具、上下文交换，Agent 循环逻辑由 Host 实现。

**调用流程**：Client 获取工具列表 → 传入模型 → 模型决策调用 → Server 执行返回结果。

**三大原语**

| 原语 | 作用 | 特点 |
|------|------|------|
| Tools | 执行动作，可修改数据 | 需权限管控 |
| Resources | 只读获取上下文 | 不改动数据 |
| Prompts | 预制提示模板 | — |

**三者分工**

- **Function Calling**：模型输出调用格式，决定调用哪个函数
- **MCP**：连接协议，打通外部系统
- **Skills**：业务 SOP，规定任务怎么做

链条：Skills 定业务规范 → MCP 接通外部 → Function Calling 模型发起调用

> MCP 不替代 Function Calling，二者配合；仅有连接无规范，Agent 会接得上但做不对。

**适用场景**
1. 多个 Agent 共用外部系统
2. 复用连接器减少自研
3. 区分只读资源与可执行工具

**PM 落地要点**
- 区分：哪些用 MCP 对接，哪些自建 Server
- Resources 只读、Tools 有副作用，分开设计权限
- 优先复用社区连接器，避免私有绑定
- 对外连接用 MCP，对内业务约束用 Skills
- 企业场景关注：安装权限、工具启用、审计日志

---

#### Skills：程序性操作手册

可版本管理；规定调用时机、参数、异常处理。

**分工**：MCP 负责接得上工具，Skills 负责用得对工具。

##### 什么是 Agent-Skill

可复用的程序性知识包（**业务操作手册**），开放标准，支持多 Agent 复用。

对比系统提示词：系统提示词全部常驻上下文；Skill 按需加载，节省 token。

> 程序性知识正在从聊天记录外化成可版本控制的仓库资产

##### 核心机制：渐进披露（Progressive Disclosure）

| 阶段 | 说明 |
|------|------|
| 发现（对话刚开启） | 启动仅加载技能 name、description |
| 激活（用户提问） | 任务匹配 description，读取完整 SKILL.md |
| 执行（真正干活） | 真正需要时，才加载脚本、参考资料 |

关键点：description 决定是否触发，描述模糊会乱触发/不触发。**（要写的短，触发词靠前，边界清晰）**

##### 概念对照

| 概念 | 核心定义 |
|------|----------|
| Workflow | 人预定义固定流程编排 LLM 与工具，确定性强、可审计 |
| Agent | 模型动态决定下一步动作，适合开放多变任务 |
| Function Calling / Tools | 模型输出结构化指令，执行单次工具动作 |
| MCP | Agent 对接外部工具、数据的连接协议（通路） |
| Skill | 可复用业务知识包，按需加载业务规范手册 |
| Subagent | 把子任务交给另一个 Agent，实现任务拆分、并行、隔离上下文 |

**链条：Workflow 是人写死流程；Agent 模型动态决策；Function Calling 做单次调用；MCP 打通外部系统；Skill 提供业务规则手册；Subagent 拆分复杂子任务。**

> Workflow vs Agent 区别：Workflow 步骤预先写死；Agent 由模型动态判断下一步，灵活性高但风险更高。

##### PM 落地判断：适合 / 不适合 Skill

- **适合**：同类任务反复出现、流程稳定、多场景复用的业务规范、操作手册，多人会话需要对齐业务逻辑，优先用 Skill，不要私藏大段 system prompt。
- **不适合**：简单一次性 API、知识需要实时服务更新、频繁改动 SDK 文档，这类交给 MCP/工具服务；Skill 维护跟不上频繁变更，会制造过时流程。

##### Skill 编写要点

把场景、触发词、排除边界写在 description；正文写执行步骤；参考资料外置到 references，避免主文件膨胀。

**Skill 验收标准**：准备该触发 / 不该触发测试用例，定义任务成功标准；上线后看误触发率、补救次数、手册是否过期。

##### 安全与评测

1. **安全**：Skill 可携带脚本指令，只加载可信来源，上线前审计，防范指令注入、恶意脚本。安全是一等约束。
2. **评测**：Skill 要有评测集，写完不等于交付，上线要验证效果。

---

#### Skill 和 MCP 关系

- **MCP**：管外部工具通路，解决怎么调用外部系统
- **Skill**：管业务流程规范，告诉 Agent 调用工具要遵守什么业务规则

> 二者互补，不是二选一。

架构默认组合：对外连接走 MCP/Tools，对内规则规范走 Skills；高风险步骤交给人工确认，三者搭配，不是互相替代。

# 三、Prompt 工程

概念：Prompt 工程化 —— 把提示词做成固定模板，只替换输入变量，实现可复用、输出稳定。

## Prompt 五大核心要素

| 要素 | 说明 | 示例 |
|------|------|------|
| **角色 Role** | 设定模型身份与看待问题的视角，决定输出风格 | "你是电商 App 的产品经理" |
| **任务 Task** | 写清楚具体产出目标，拒绝模糊指令 | 差："帮我总结用户反馈" 好："阅读 30 条反馈，提炼本周 Top3 高频问题" |
| **上下文 & 约束 Context** | 给模型业务参考资料（RAG 检索出的文档）；约束：数据源、字数、禁止编造、脱敏规则 | — |
| **Few-shot 示例** | 提供输入输出样例，教会模型判断逻辑与格式 | 3-5 个高质量样例，覆盖边界 case |
| **输出格式 Output** | 结构化（JSON/XML）可被程序直接解析；只口头说"输出 JSON"可靠性不足 | 显式规定结构 |

### 推理模型时代提示词变化

| 厂商 | 变化 |
|------|------|
| OpenAI | 推理模型（o 系列）自带思考能力，强制分步指令反而限制解法；非推理模型 CoT 依旧有效 |
| Google | 推理模型内部自动思考，反复写"一步步思考"会增加 token、拉高成本 |
| Anthropic | thinking 是模型内置能力，不完全靠 Prompt 逼出来 |

> 考点：不要无脑到处复制"请一步步思考"。

---

## 结构化输出 JSON

### 一、为什么需要结构化输出

模型输出交给后端代码解析时，字段名、数据类型、结构必须固定；只输出自然语言，程序无法读取，Demo 不能直接上线。

### 二、结构化输出四个发展阶段

| 阶段 | 说明 | 问题 |
|------|------|------|
| 1. 口头 Prompt 要求输出 JSON | 只写"输出 JSON" | 模型容易输出多余话术、字段写错、依赖正则清洗，稳定性差 |
| 2. JSON 模式（legacy） | 保证 JSON 语法合法 | 不保证业务字段、数据类型正确，字段缺失依旧导致下游报错 |
| 3. Tool Use / Function Calling | 把输出结构定义为工具入参 schema | 遵从率约 86%，达不到生产 100% 可靠 |
| 4. 原生 Structured Outputs | 约束解码，token 生成层面限制输出 | **2026 生产首选**（Claude、OpenAI、Gemini 均已支持） |

### 三、Schema 设计 7 条核心规则（PRD 直接用）

1. 尽量扁平，避免深度嵌套
2. 每个字段补充 description 描述，消除歧义
3. 固定取值场景优先用 enum 枚举
4. 明确标注 required 必填字段
5. 开启 additionalProperties: false
6. 示例字段顺序与 schema 顺序保持一致（Gemini 对顺序敏感）
7. 优先用 Pydantic/Zod 代码库自动生成 schema

### 四、失败兜底：校验 + 重试

**失败场景**
1. 安全策略触发，模型拒绝回答
2. max-token 截断，JSON 输出不完整
3. 语法合法，但业务语义、大小写等细节偏差

**生产稳定流程**
1. 使用官方结构化输出 API
2. 应用层做业务校验
3. 校验失败：重试，处理临时错误
4. 重试失败：执行降级/人工兜底
5. 失败样本回流，反向优化 Schema

> ⚠ 核心考点：开启 Structured Outputs ≠ 不用校验，接口只保证语法合法，不保证业务语义正确。

### 五、PM 写 PRD 要求

1. 写明完整字段契约：字段名、类型、required、enum、示例
2. 明确定义失败产品策略：拒绝、截断、校验失败分别如何体验
3. 技术方案优先选官方 Structured Outputs / 工具调用，禁止只靠 prompt 文字约束 JSON

## 系统提示词设计

### 1. System Prompt 与用户输入分层

| 层级 | 说明 |
|------|------|
| system | 全局设定，角色、语气、能力边界、输出格式；优先级高于用户输入 |
| user | 用户真实提问输入 |
| assistant | 模型历史回答 |

> 业务要点：产品人格、约束统一放在 system，作为产品配置管理。

### 2. System Prompt 需要写的 3 类内容

1. **身份与语气**：产品角色、说话口吻，固化在系统层
2. **能力边界**：明确可回答、拒绝回答；超纲问题处理策略
3. **兜底话术**：检索失败、模型报错、结构化输出失败时固定文案，产品定义，不交给模型随机生成

### 3. Prompt 注入（Prompt Injection）

含义：用户输入夹带恶意指令，试图绕过 system 系统设定篡改模型行为。

**PM 三点意识：**
1. system 不是绝对安全防火墙
2. **权限最小化**，Agent 工具、访问数据范围尽量收紧
3. 高风险操作**增加人工确认**，不能完全交给模型自动执行

### 4. Prompt 版本管理

1. Prompt 改动少量文字就会改变输出，不能直接复制上线
2. 拆分固定模板（system/指令）和变量（用户输入、检索材料），分开存储
3. 修改必须记录版本号、变更原因；支持版本回滚

### 5. 回归测试 & 评测集

1. 修改 prompt 必须跑回归测试；大模型存在随机性
2. 评测集：业务测试 case 集合，迭代 prompt 就要反复执行
3. 不能只靠肉眼看几个样例就上线

> **任何一次修改都应该在评测集上跑一次再合并**

### 6. 灰度发布

1. 评测集通过 ≠ 直接全量上线，评测集无法覆盖线上全部长尾输入
2. 小流量灰度，监控真实业务指标
3. 新旧版本可切换，异常可以快速回滚
4. Badcase 回流：线上错误案例补充进评测集，后续迭代自动防护

### 7. 完整 Prompt 工程流水线

```
需求/Badcase 收集
  → 起草 Prompt（角色/任务/约束/示例/输出格式）
    → 模板化：拆分「固定模板」与「变量」，纳入版本管理
      → 评测集回归测试（哪怕只改一个词）
        → 人工抽查显著变化的用例
          → 小流量灰度 + 业务指标监控
            → 全量上线
              → 持续监控 → 新 Badcase 回流评测集 → 下一轮迭代
```

## CoT 思维链

### 1. 定义

CoT（思维链）：Prompt 技术，让模型先输出中间推理步骤，再给出答案，不需要微调模型，修改提示词即可。

### 2. CoT vs 直接提问

| | 直接提问 | CoT |
|------|----------|-----|
| 输出方式 | 直接输出答案 | 先推理再给结论 |
| 复杂任务 | 容易跳步出错 | 提升准确率 |
| 可解释性 | 推理黑盒 | 能看到推理过程 |
| 代价 | token 少、延迟低 | token 增加、延迟升高 |

### 3. 核心优势

1. 擅长多步计算、业务规则嵌套等复杂推理
2. 可解释：能看到推理过程，适配合规、审核场景
3. 零训练成本，依靠 Prompt / few-shot 实现
4. 错误可定位，方便 badcase 归因迭代

> ⚠ 局限：不能保证每一步推理都正确，不能解决知识库缺失带来的幻觉。

### 4. 开启方式

1. **普通 CoT**：Prompt 直接加指令「请一步步分析，再给出结论」
2. **few-shot CoT**：推理效果不稳时，给示例：输入 → 推理步骤 → 最终答案；1-3 个高质量示例即可

### 5. 成本取舍原则

> 只有答错的业务损失 > token + 延迟成本，才默认开启 CoT；不要全站无条件开启。

**落地策略**：
- 任务分流：简单问答直接输出，复杂任务启用 CoT
- 分类器触发：轻量模型判断是否需要推理，动态决定是否加 CoT 指令
- 展示折叠：推理过程可折叠，前端默认只展示最终答案
- 长度约束：限制推理最大步数、字数

### 6. CoT + 结构化输出

- 分工：CoT 负责思考推理，JSON 结构化输出负责交付最终结果给下游
- 要求：推理文本与 JSON 结果分区，不能混杂在一起，PRD 要明确约定

### 7. 延伸考点

**Self-Consistency（自一致性）**
- 原理：对同一问题多次采样多条推理路径，结果投票聚合
- 代价：调用次数上升，token、延迟大幅增加
- 适用：高风险审核、离线处理；实时聊天一般不使用

**CoT + RAG**
- RAG：获取外部参考资料；CoT：对拿到的资料做推理分析
- Prompt 约束：推理仅限使用检索到的内容；资料不足输出「无法判断」，防止幻觉
